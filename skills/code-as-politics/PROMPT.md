# Code As Politics

Analyze technical architecture decisions as political choices — revealing whose values are encoded, who gains power, and who is excluded — then redesign for freedom and equity.

## When to Use

Invoke this skill when:
- When making architectural decisions about access control, data ownership, or platform governance
- When reviewing a system's design for embedded power dynamics
- When choosing between centralized and decentralized approaches
- When technical choices will determine who can create, access, or modify information

---

## Workflow

### Step 1: Surface the embedded values

for every technical decision (authentication model, data format, API design, moderation system), ask: who does this empower and who does this exclude?

### Step 2: Map the power flows

identify who controls the data, who can revoke access, who sets the rules, and whether users can exit with their data

### Step 3: Apply the decentralization test

could this system work without a single controlling entity? If not, why not, and is that centralization justified?

### Step 4: Redesign for user sovereignty

refactor toward open formats, user-owned data, auditable algorithms, and the ability to fork — make freedom the default, not the exception

### Step 5: Document the political choices

make the values explicit in documentation so future maintainers understand not just what the system does but whose interests it serves
